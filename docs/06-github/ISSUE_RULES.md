# GitHub 이슈 생성 규칙

> 이 문서는 Claude Code를 포함해 이 프로젝트에서 GitHub 이슈/브랜치를 다루는 모든 주체가 따라야 하는 규칙이다. 하위 기획서 작업을 시작할 때 반드시 이 문서를 먼저 읽는다.

## 원칙

**하위 기획서 파일 1개 = GitHub 이슈 1개.** `docs/03-backend/00-bugfix-security.md` 같은 파일이 만들어지고 사용자 확인을 받으면, 그 시점에 대응하는 이슈를 하나 만든다. 기획서와 이슈는 항상 1:1로 대응해야 하고, 어긋나면 안 된다 (기획서 따로 이슈 따로 관리되다 어긋나는 걸 방지하는 게 목적).

## 이슈 생성 시점

1. 하위 기획서 작성 → 사용자 확인 완료 (`docs/CLAUDE.md`의 작업 절차 2번)
2. 확인 완료 직후, **코드 작업 시작 전에** 이슈부터 생성
3. 이슈 생성 후 그 이슈 번호로 브랜치를 만들고 작업 시작

## 이슈 제목 형식

```
[<영역>] <번호>. <하위 기획서 제목>
```

- `<영역>`: 하위 기획서가 속한 폴더명 기준 — `backend` (`docs/03-backend/`) / `app` (`docs/04-app/`) / `db` (`docs/05-db/`)
- `<번호>`: 하위 기획서 파일명 접두 번호 두 자리 그대로 (`00`, `01`, ...)
- `<하위 기획서 제목>`: 파일의 첫 번째 `#` 헤딩에서 번호 부분 뗀 나머지

예: 파일 `docs/03-backend/00-bugfix-security.md`, 첫 줄이 `# 00. 백엔드 프로젝트 초기 세팅 + 알려진 버그/보안 이슈 선반영`이면
→ 이슈 제목: `[backend] 00. 백엔드 프로젝트 초기 세팅 + 알려진 버그/보안 이슈 선반영`

## 이슈 본문 형식 (머신 리더블 — 아래 구조 그대로 채울 것)

```markdown
## 하위 기획서
docs/03-backend/00-bugfix-security.md

## 마스터 기획서 대응 항목
마스터 기획서 8장 "개발 순서" 1번

## 작업 항목
- [ ] (하위 기획서의 "무엇을 하는가" 섹션 각 항목을 체크박스로 그대로 옮김)
- [ ] ...

## 영향 범위
(하위 기획서의 "영향 범위" 섹션 그대로 옮김)

## 완료 조건 (Definition of Done)
- [ ] 위 작업 항목 전부 완료
- [ ] 빌드/테스트 통과
- [ ] 마스터 기획서·하위 기획서와 실제 구현이 어긋나는 부분 없음 (있다면 이 이슈에 코멘트로 남기고 필요 시 마스터 기획서 갱신)
```

## 라벨 (전체 목록, `.github/labels.yml`에 정의 — `gh label sync -f .github/labels.yml`로 리포에 적용)

**영역 (area, 이슈 하나에 정확히 1개)**
- `area:backend` — `docs/03-backend/`
- `area:app` — `docs/04-app/` (Flutter)
- `area:db` — `docs/05-db/`
- `area:design` — `docs/02-design/`
- `area:infra` — 배포/CI/환경 설정

**종류 (type, 복수 부여 가능)**
- `type:feature` — 신규 기능
- `type:bugfix` — 기존 버그 수정 / 알려진 버그 선반영
- `type:security` — 보안 이슈 대응
- `type:refactor` — 동작 변경 없는 구조 개선
- `type:docs` — 기획서/문서 정리, 코드 변경 없음

**기타**
- `blocked` — 다른 이슈나 외부 요인(키 발급, 인프라 준비 등)에 막혀 진행 불가

이슈는 영역 라벨 1개 + 종류 라벨 1개 이상을 반드시 붙인다. 상태는 별도 라벨 없이 GitHub 기본 Open/Closed로만 관리 (라벨 과다 방지).

## 브랜치 전략: `main` / `dev` 2-스테이지

- `main`: 배포 브랜치. **항상 배포 가능한 상태만 유지**, 보호 브랜치로 설정 (직접 push 금지, PR만 허용)
- `dev`: 통합 개발 브랜치. 모든 작업 브랜치는 여기로 모인다
- 작업 브랜치: `dev`에서 분기, 작업 끝나면 `dev`로 PR

```
<영역>/<번호>-<슬러그>
```

예: `backend/00-bugfix-security`, `app/01-home`

이슈 제목의 번호·영역과 항상 일치시킨다. 슬러그는 하위 기획서 파일명에서 번호 접두어를 뗀 나머지를 그대로 쓴다.

`dev → main`은 별도 릴리즈 PR로만 진행한다 (배포 준비됐을 때, 여러 작업 브랜치가 `dev`에 쌓인 걸 한 번에 승격). 작업 브랜치가 `main`으로 직접 PR 나가는 일은 없어야 한다.

## PR 규칙

- **모든 작업은 PR로만 머지한다.** `dev`에 직접 push 금지
- PR 베이스는 항상 `dev` (릴리즈 PR만 예외로 `dev → main`)
- PR 설명 첫 줄에 `Closes #<이슈번호>` 반드시 포함 → merge 시 이슈 자동 종료
- PR 제목은 이슈 제목과 동일하게
- 완료 조건(DoD) 체크박스를 PR 설명에도 그대로 복사해서 실제로 다 체크됐는지 확인 후 머지
- 템플릿: `.github/ISSUE_TEMPLATE/sub-spec.md` (이슈), `.github/pull_request_template.md` (PR) — 새로 만들 때 항상 이 템플릿 기준으로 채운다

## 하지 말아야 할 것

- 하위 기획서 없이 이슈부터 먼저 생성 (순서 거꾸로 금지)
- 이슈 하나에 하위 기획서 여러 개 몰아넣기 (1:1 대응 깨짐)
- 이슈 본문을 위 머신 리더블 구조 없이 자유 서술로만 작성 (자동화·추적이 안 됨)
