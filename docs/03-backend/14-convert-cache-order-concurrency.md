# 14. 변환 캐시 순서 버그 + 동시 요청 버그 수정

## 목표
`ConvertService.convert()`의 두 가지 문제를 고친다.
1. 캐시 히트여도 원문 크롤링을 매번 함 (크롤링이 캐시 조회보다 먼저 실행됨) — QA 보고서에서 캐시 히트가 1.1초 걸린 원인
2. 같은 기사·스타일·레벨 요청이 동시에 들어오면 AI를 두 번 호출하고, 두 번째 저장에서 UNIQUE 제약 위반 예외로 500 응답

## 무엇을 하는가
1. 순서 변경: URL로 `news_articles` 조회 → 기사가 있으면 `(article_id, style, level)` 캐시 조회 → **히트면 크롤링 없이 바로 반환**. 기사가 없거나 캐시 미스일 때만 크롤링 + AI 호출
2. 동시성 1차 방어: 캐시 키 `articleId:style:level` 단위 락(`ConcurrentHashMap` + 키별 락 객체). 락 안에서 캐시를 한 번 더 확인 → 먼저 들어온 요청이 저장한 결과를 뒤 요청이 그대로 사용, AI 호출 1회
   - AI 호출(최대 수십 초) 동안 DB 트랜잭션을 잡고 있지 않도록, 크롤링·AI 호출은 트랜잭션 밖에서 하고 저장만 짧은 트랜잭션으로 분리
3. 동시성 2차 방어(세이프티넷): 캐시 저장 시 UNIQUE 위반(`DataIntegrityViolationException`)이 나면 예외를 던지지 않고 그 키로 다시 조회해서 반환 — 나중에 서버를 여러 대로 늘려서 1차 락이 안 먹혀도 500이 안 나게
4. 같은 이유로 신규 기사 저장(`news_articles` URL UNIQUE)도 동시 요청 시 같은 방식으로 처리

## 영향 범위
- `backend/src/main/java/.../domain/convert/service/ConvertService.java`
- (필요 시) 저장 전용 트랜잭션 메서드를 위한 작은 헬퍼 클래스 신규
- API 요청/응답 형식 변경 없음 — 앱 수정 불필요

## 완료 기준 (테스트로 확인)
- 캐시 히트 시 `CrawlingService.crawl()` 호출 0회
- 같은 키로 동시 요청 10개 → AI 변환 호출 1회, 10개 모두 200, `conversion_cache` 행 1개
- 서로 다른 레벨 요청은 각각 따로 변환됨
- 기존 13번 테스트 전부 통과

## 작업 중 발견해서 같이 고친 것
- **변환할 때 고른 용어 난이도가 사용자 정보에 저장되지 않던 버그**: `ConvertService`가 인증 필터에서 받은 `User`(트랜잭션 밖에서 읽은 detached 객체)의 `lastGlossaryLevel`을 바꾸고 있어서 DB에 반영이 안 됐음 (QA BUG-02와 같은 원인). 변환 결과 저장 트랜잭션 안에서 사용자를 다시 읽어서 갱신하도록 수정. 테스트로 재현 → 수정 확인.
- 이 버그 때문에 `lastGlossaryLevel`은 지금까지 항상 `MEDIUM`이었음 — 앱 10번 작업(레벨 기본값을 이 값으로)이 의미 있으려면 이 수정이 먼저 필요
